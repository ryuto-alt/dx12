# シーンファイル形式 v2 設計書（大規模シーン対応）

2026-10-01 確定。正本は**テキスト（JSON）のまま**形を変え、実行用は将来ビルド時にバイナリへ変換する二段構えにする。

## 0. 現状と問題（実測）

大規模シーンの例 `dead_mall.json`（Dreamcore 移植）: **15.7MB・66.9 万行・14,774 体**（1 体 ≈ 1KB・45 行）。

| 問題 | 中身 |
|---|---|
| 既定値の書き出し | 静的剛体の設定一式・`meshCollider.offset:[0,0,0]`・`rotation:[0,0,0]`・`scale:[1,1,1]` を全員が書いている |
| float32 のノイズ桁 | `0.019999999552965164`（本来 `0.02`）。float を double として dump しているため |
| 整形 | `dump(2)` で 1 体 45 行。grep で 1 体が取れない・AI が読めない |
| 親の配列番号 | `parent`（index）を `parentGuid` と二重に書いている。index は挿入・削除で全体がずれ差分が広がる |
| 同一メッシュの大量配置 | `SM_Module07 x1070` のように同じモデルを個別エンティティで持つ |
| 丸ごと読み | 1 ファイルを全部パースするしかない（部分ロード・ストリーミング不可） |

試算: 既定値の省略＋最短 float＋1 行 1 体で **15.7MB → 4.9MB（-69%）・66.9 万行 → 約 1.5 万行**。

## 1. 確定した判断（蒸し返さない）

- **正本はテキスト**。AI の grep・git の差分とマージ・スクリプトからの直接書き出し（MCP `dx12_scene_write` / Python 生成）が最重要の利用者だから。
- **正本に使わないもの**: バイナリ / FlatBuffers / MessagePack / CBOR（AI と git から中身が見えない）、SQLite（差分とマージ不可。エディタの索引キャッシュ用途ならあり）、YAML（遅い・曖昧）。
- **JSON Lines ではなく「正しい JSON のまま、entities 配列だけ 1 行 1 体」**。既存の全ツール（Python `json.load`・TS `JSON.parse`・`RewriteAssetPathRefsInFiles`・外部スクリプト）がそのまま読めることを優先する。
- **実行用バイナリは後段**（段階 3）。段階 1 で読み込み時間の内訳を測ってから範囲を決める。
- **Play の一時スナップショット（`SaveToString` / `LoadFromString`）は v1 の完全形のまま**（速度優先。省略・整形はファイル保存の経路だけ）。

## 3. 段階 1 の仕様（形式 v2）

### 3.1 ファイルの見た目

```json
{
  "version": 2,
  "postProcess": { ... 従来どおり整形 ... },
  "skybox": { ... },
  "entities": [
{"guid":"cdceadd6d17c8bca","name":"Dead_Mall","transform":{"position":[0,0,0]}},
{"guid":"12f903ab6e26d879","material":{"metallic":1.0,"roughness":0.1},"meshCollider":{},"meshRenderer":{"modelPath":"models/dm/SM_Module04_Glass.glb"},"name":"SM_Module04_Glass_0451","parentGuid":"86cf1bddaed44451","rigidBody":{},"transform":{"position":[-394.4345,0.195,332.35]}}
  ]
}
```

- ルート直下のシーン設定は従来どおり `dump(2)` 相当の整形（小さく、人が読むため）。
- `entities` 配列だけ **1 要素 1 行・区切りなし（`,`/`:` の後に空白なし）**。キー順は nlohmann の既定（辞書順）。
- 末尾改行あり。改行は `\n`。

### 3.2 既定値の省略（固定の既定値表）

- **表**: `src/scene/scene_defaults_v2.json`（リポジトリにコミットする**凍結データ**）。形は `{ "<コンポーネントキー>": { "<フィールド>": <既定値>, ... }, ... }`。`transform` は `{"rotation":[0,0,0],"scale":[1,1,1]}`。
- 表はビルド時にヘッダへ埋め込む（Game.exe でも使う。実行時にファイルを探さない）。TS 側（`tools/mcp-server`）も同じ JSON を読む。**唯一の正本はこの 1 ファイル**。
- **表は凍結**。構造体の既定値をあとで変えても表は変えない（既存シーンの見た目が変わらないことが最優先。`gi.mode` と同じ方針）。表を変えたいときは `scene_defaults_v3.json` と `version: 3` を新設し、古い表は消さずに残す。
- 表の初期値は「既定構築したコンポーネントを**実際の保存処理**で直列化した結果」から作る（作成用の補助を用意し、生成物をコミット）。保存処理が既定時に書かないフィールドは表に入れない（読み込み側で「キーがある」ことに意味がある場合の事故を避ける）。
- **例外: `rigidBody` だけは表の値を「静的コライダー」（motionType 0 / mass 0 / friction 0.8 / restitution 0 / 重力なし）にした**（2026-10-01 実装時に確定）。大規模シーンの剛体はほぼ全部が静的コライダーで、既定構築（動的）を表にすると Dead Mall が 5.9MB になり F3 を満たさないため。**v2 ファイルの `"rigidBody":{}` は静的**を意味する（v1 では従来どおりローダーの既定）。手書きで動く剛体を書くときは `motionType` を明示すること。
- **省略（保存時）**: エンティティの各キー K が表にあり値がオブジェクトなら、表と**完全一致**するフィールドを消す。全部消えたら `{}` を残す（キーの存在＝コンポーネントがある）。一段だけ（入れ子は再帰しない。配列は丸ごと比較）。
- **補完（読み込み時）**: `version >= 2` なら、キー K が表にありオブジェクトなら、表にあって欠けているフィールドを足す。**補完後の JSON は v1 で保存したものと同じ**になる＝下流の `InstantiateEntityJson` は一切変えない。
- 補完は `ApplySceneJson` の入口（=全経路: ディスク・VFS/pak・`LoadFromString`）と `ApplyOverrides` で行う。

### 3.3 最短 float

- ファイル保存時、数値が float32 で正確に表せる double（`(double)(float)v == v`）なら、**float32 として往復する最短の十進表記**（`std::to_chars(float)`）に置き換える。それ以外の double は触らない。
- 読み込むと同じ float32 に戻るので、値は 1 ビットも変わらない。
- 表の値も同じ正規化をした状態で持ち、比較は正規化後に行う。

### 3.4 親参照

- `parentGuid` を書くときは `parent`（index）を書かない。読み込みは従来どおり両対応（旧ファイル・手書き JSON は index も可）。

### 3.5 互換

- 読み込み: v1（`version` 無し / 1）は従来どおり。v2 は補完してから従来の処理。
- 保存: シーンファイルは常に v2。**v2 で保存したシーンは v2.1 より前のエンジンでは正しく開けない**（リリースノートに明記）。
- `.prefab` は段階 1 の対象外（`version: 1` のまま）。
- `RewriteAssetPathRefsInFiles` がシーンファイルを書き戻すときは v2 の整形で書く（`dump(2)` で崩さない）。
- MCP（TS）: シーンファイルを読むコードは補完してから使う。書くコードはどちらの形でもよい（エンジンが読める）が、`sceneWrite.ts` の検証は省略形を受け付けること。

### 3.6 合否基準

| # | 基準 | 測り方 |
|---|---|---|
| F1 | **等価性**: v1 シーン → v2 保存 → 読み込み → `SaveToString`（完全形）が、v1 を直接読んだ `SaveToString` と**バイト一致** | 実プロジェクトのシーン（scratchpad へのコピー）全件 |
| F2 | 純関数の往復: 全エンティティで `inflate(strip(normalize(e))) == normalize(e)` | ctest（GPU 不要） |
| F3 | サイズ: Dead Mall 15.7MB → **5MB 以下**、行数 **約 1.5 万行** | 実測 |
| F4 | 保存時間・読み込み時間が v1 より悪化しない（内訳ログで比較） | Dead Mall / PerfTest stress_100000 |
| F5 | 既存 ctest・MCP の TS テスト全通過 | ctest / `npm test` 相当 |
| F6 | ビルドしたゲーム（Game.exe・pak）で v2 シーンが開ける | 使い捨てプロジェクトで `--build` |

### 3.7 読み込み時間の内訳ログ（段階 3 の判断材料）

`Load` で「ファイル読み（VFS/pak 復号込み）」「JSON パース」「補完」「エンティティ生成（うちモデル読み込み）」「親子復元」の ms を `Logger::Info` に 1 行で出す。

### 3.8 段階 1 の実測結果

- 実プロジェクト 37 本で v1/v2 の等価性がバイト一致（F1）。Dead Mall 15.65MB・66.9 万行 → **4.89MB・15,074 行**。37 本合計 192.6MB → 83.1MB。
- 読み込み: Dead Mall 934 → 892ms、stress_100000 6084 → 5955ms。保存: 196 → 152ms、893 → 740ms（並列化）。
- **読み込みの内訳: パース＋補完は 6〜8%。85〜90% はエンティティ生成（ほぼ全部 `Scene::Spawn` のモデル読み込み）**。

## 4. 段階 2〜4 の方針（段階 1 の計測後に詳細化）

**段階 1 の内訳を受けて順番を変更: 段階 4 のインスタンス群（＋`Spawn` の軽量化）を段階 2・3 より先にやる。** 実行用バイナリ（段階 3）で縮むのは読み込みの 6〜8% だけなので最後に回す。


- **段階 2（分割）**: `foo.json`（ルート設定＋割り当てなしのエンティティ）＋`foo.parts/<セルまたはレイヤー>.json`（同じ 1 行 1 体）。単位はルートエンティティのサブツリー（親子をファイルで分断しない）。保存は変更のあった部分だけ書く。
- **段階 3（実行用バイナリ）**: 段階 1 の内訳でパース＋補完が読み込みの 1 割未満なら優先度を下げ、モデル読み込み側（既存の読み込み最適化）を先にやる。
- **段階 4（インスタンス群＋ストリーミング）**: 同一モデル・同一マテリアルの静的配置を `instanceGroup`（model＋transform 配列、巨大ならバイナリのサイドカー）に。既存の描画インスタンシングへ直結。ストリーミングは段階 2 のセルを単位にする。
